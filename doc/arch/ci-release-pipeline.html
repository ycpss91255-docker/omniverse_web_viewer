1. Release Invariant

owv 的核心發佈規則（#70 起）：沒有任何版本可以在 Tier B visual acceptance 通過之前發佈。這個規則由 CI pipeline 的 job dependency chain 結構性保證，不靠人為紀律。

v0.3.0-rc1 事件：rc1 發佈時 Tier B 從未對該 commit 執行過。tag push 跳過了 GPU job，Release 照常 cut。從此之後，tier-b-visual-e2e 成為 call-release 的硬 needs。沒有 override input、沒有 continue-on-error、沒有 if: always() 逃生門。

4. Picture Gate 多層防禦

為什麼只看 job status 不夠？Review round 8 產出了 5 種 single-step edit 可以讓 tier-b-visual-e2e 保持綠色但實際上沒有跑 acceptance spec：

#手法為什麼 job 仍然綠色
1Truncate driver: : > script/ci/tier_b_visual_e2e.sh --print-x--print- 不在 checker whitelist
2sed -i '1a exit 0' script/ci/*.shglob 不是 pinned path
3$GITHUB_PATH entry shadowing bashjob 用的 bash 是 stub
4Job-level container: whose bash is a stub同上
5echo TIER_B_PRODUCER_IMAGE=busybox >> "$GITHUB_ENV"producer 是 no-op image

所有 5 種手法的共同結果：沒有 frame 被 sample。require-picture-evidence 檢查的是 attestation output（由 Playwright spec 在 sample frame 後寫入），空值 = 拒絕發佈。

5. Image Recovery Dispatch

image push 失敗時的恢復路徑：以 tag ref dispatch workflow，帶 publish_image_tag。

call-release stand-down：dispatch 帶 publish_image_tag 時，call-release 不跑（Release 已存在）。publish-image 允許 call-release == skipped，但 tier-b 必須 success -- recovery dispatch 不繞過 picture gate。publish-image 另有 Release 存在性檢查（沒有 Release 不推 image），確保 stand-down 安全。

6. 故意不加 if: 的設計

verify-tag-shape 和 verify-tag-on-main 沒有 if: 條件。這不是遺漏：

有 if:

Non-tag ref 時 job 被 skipped。GitHub default: a skipped need skips its dependent。tier-b-visual-e2e needs 這兩個 job，所以 nightly schedule 的 tier-b 也會被 skip -- 但 nightly 正是要跑 tier-b 的。

沒有 if:

Job 永遠 success（tag check 用 per-step guard）。Nightly 的 tier-b 不會因為 skipped need 被 skip。成本：nightly 多跑一個 cheap hosted job。

tier-b-visual-e2e 的 if: 也故意不含 status function（沒有 always() / !cancelled() / success()）。GitHub default rule: job is skipped when any need did not succeed。GPU runner 不可用 → tier-b timeout/fail → call-release blocked, not waved through。
