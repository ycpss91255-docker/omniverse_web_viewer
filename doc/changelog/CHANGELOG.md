# Changelog

## [Unreleased]

### Changed
- CI: a Tier B run that is CANCELLED on a tag ref now fails the workflow loudly instead of blocking the release in grey. `cancel-in-progress: false` protects a RUNNING Tier B but not a QUEUED one -- GitHub cancels the previously pending member of a concurrency group when a new run enters it, so a tag's Tier B waiting behind the nightly is cancelled outright by any third entrant. The consequence already failed closed (`call-release` skips on a non-success need, `publish-image` requires `result == 'success'`), so nothing unsafe could publish; what was missing is the signal. The pushed tag produced no Release and no image, and the only trace was a grey cancelled job -- while the comment two lines above told the maintainer the opposite would happen ("QUEUES behind it instead of cancelling it"). That comment is corrected, and a new report-only `release-blocked-report` job turns the silence red. It is deliberately incapable of being an override: nothing `needs` it, so it can only ADD a failure, never allow a publish.
- CI: the push trigger now matches the VERSION shape (`v[0-9]+.[0-9]+.[0-9]+` and its `-PRERELEASE` sibling) instead of `v*`, and a new `verify-tag-shape` job makes the check authoritative. `v*` accepted tag names `script/ci/derive_image_tag.sh` hard-rejects -- `v2`, `vnext`, `vlatest` -- and that rejection lived in `publish-image`, the last job in the chain, which `needs` a successful `call-release`. So such a tag cut a real GitHub Release first and only then failed on the version grammar, producing exactly the Release-without-an-image state the file argues against, after spending up to the full 60-minute Tier B budget on the shared GPU, and leaving the run red in a way that reads as a gate failure rather than a naming mistake. The globs alone do NOT close that: GitHub's tag filters have no alternation and no anchored character classes, so `v[0-9]+.[0-9]+.[0-9]+-*` accepts any pre-release suffix and `v1.2.3-`, `v1.2.3--`, `v1.2.3-rc_1`, `v1.2.3-rc1.`, `v1.2.3-rc1+b` all pass the trigger and are all rejected by the deriver -- while narrowing the glob would instead make a legitimate `v1.2.3-rc.1` silently not trigger. `verify-tag-shape` therefore runs the deriver itself, before anything irreversible, and is a `needs` of both `call-release` and `tier-b-visual-e2e`. It carries no `if:` on purpose: a job that never skips can be needed by the GPU gate without forcing a status function onto that gate's own condition.

### Security
- **BREAKING (published bundles):** the `?server=&port=&media=` target override no longer works in a built viewer. It was documented in `resolveTarget.js` as an `npm run dev` convenience, but it was compiled into the PUBLISHED bundle and it OUTRANKED the operator-configured target. With `nativeTouchEvents: true` (`packages/stream-core/src/buildStreamConfig.js`), anyone who could hand a viewer user a URL could repoint the stream at a host of their choosing AND have that user's keyboard, mouse, wheel and touch input forwarded there, full-screen, on a trusted origin, with nothing on the page indicating it -- proven end to end through the production entrypoint. The `^[A-Za-z0-9.-]+$` server check is a CHARSET check that permits arbitrary hostnames, so it was never a mitigation. `resolveTarget()` now takes an explicit `allowQueryOverride` argument that defaults to false, and `main.ts` passes `import.meta.env.DEV` -- true only under the Vite dev server, replaced with `false` by `vite build`. The dev workflow the override exists for is therefore unchanged (including the example demo's documented "Run it (dev)" query string), while a shipped viewer takes its target from the entrypoint render alone. The same change applies to `examples/embedded-site-demo`. Six unit tests were updated to opt in and four added to lock the default; node 82 -> 86.
- Tier B: the Kit producer is pinned by DIGEST instead of the mutable `isaac-stream-source:0.0.1` tag. That container is the strongest thing this repo runs -- root (isaac#244), `--network=host --ipc=host --gpus all`, on a persistent self-hosted GPU runner -- yet it was the one left resolving through a tag, while the `busybox` twenty-five lines earlier in the same job is digest-pinned and the workflow states the reason ("runs as root with the workspace bind-mounted, BEFORE checkout, on a persistent self-hosted GPU host") and separately states that "GHCR tags are MUTABLE". isaac#244 is an OPEN defect in that image, so a re-push under the same tag is likely rather than hypothetical. The digest was re-resolved from the registry rather than copied from a report. `TIER_B_PRODUCER_IMAGE` still overrides it for a one-off, and the workflow's separate pull step now asks the driver for the reference (`--print-producer-image`) instead of carrying a second copy of the pin that could drift from the one actually run. bats 54 -> 55.
- Entrypoint: `/etc/host.yaml` keys are now read from their own section instead of from anywhere in the file. `yaml_value` matched `^[[:space:]]*<key>:` -- any indentation, any section, first hit wins -- and that file is BY DESIGN shared with the other containers on the host (the entrypoint's own comment cites isaac#65; the live isaac `host.yaml` already carries a second top-level `livestream:` block, so a colliding key is ordinary rather than exotic). Verified: a foreign `ui_mode:` failed our enum and the container refused to boot on a key never addressed to it, and a foreign `public_ip:` in an EARLIER section won outright -- the viewer then dialled the wrong host silently, with exit 0 and HTTP 200, so nothing in the image or in CI said anything was wrong. The lookup is now scoped to `network:` / `viewer:`, i.e. only the keys this file's documented schema defines can steer the viewer, and two bats cases lock both halves. bats 52 -> 54.
- The dependency tree that produces the shipped bundle is now committed and installed with `npm ci`. No lockfile existed anywhere in the repo and every stage used `npm install`, so the tree was resolved fresh on each build: `vite` (`^5.2.0`) and its esbuild dependency EXECUTE at build time and emit the exact JavaScript that ships in the public GHCR image, and every transitive dependency was wholly unpinned -- a compromised release anywhere in those ranges would have been incorporated silently. There was also no way to answer, after the fact, what was actually in `0.3.0-rc3`: the build was not reproducible, so a compromise could not have been scoped or a clean rebuild proven. A root `package-lock.json` for the npm workspace is now committed (pinning what the ranges resolve to today: vite 5.4.21, typescript 5.9.3, eslint 8.57.1, @typescript-eslint 7.18.0, alongside the already-exact `@nvidia/omniverse-webrtc-streaming-library@5.6.0`), and `stream-only-build` + `example` install with `npm ci`, which also fails loudly on lock drift instead of silently re-resolving. **Residual gap, stated rather than hidden**: `usd-viewer-build` and `devel` install from the upstream `web-viewer-sample` submodule, which ships no lockfile and which D2 says is built UNMODIFIED, so that one tree is still resolved fresh -- closing it needs either an upstream lockfile or a decision to layer one of ours onto the sample.
- The release-blocking picture gate no longer runs on an unpinned toolchain. `test/e2e` declared `"@playwright/test": "^1.44.0"`, gitignored its `package-lock.json` and installed with `npm install`, so the Playwright minor and the Chromium build that gate every release were decided at image-build time rather than by the commit -- two builds of the same tag could gate differently, an upstream minor could change what the suite enforces (it relies on repeated `--project` selection, `expect.poll` with custom `intervals`, and `retain-on-failure` tracing) with no repo change to bisect, and "Tier B passed on that commit" was not reproducible after the fact. That matters because `tier-b-visual-e2e` is a hard `needs` of `call-release` and `publish-image` with no override, so anything that breaks the gate blocks every release. The lockfile is now committed (dropped from `test/e2e/.gitignore`), the Dockerfile uses `npm ci`, and the version is pinned exactly (`1.62.1`) so a bump is an explicit PR that re-runs the gate.
- CI: the `workflow_dispatch` publish escape hatch can no longer overwrite a released version. `publish_image_tag` accepted any semver-shaped string from any non-tag ref -- `derive_image_tag.sh` checks only the SHAPE -- and GHCR tags are mutable, so one dispatch from `main` with `publish_image_tag=0.3.0` would have silently replaced the image behind the v0.3.0 Release with a build of arbitrary branch code, leaving the downstream pin (isaac#173) running code no Release points at. The same input could also mint a version-tagged image with no Release at all, which the file itself calls out as "a dangling artifact a consumer could pin". `publish-image` now requires, on the non-tag path only, that a published Release `v<version>` already exists AND that the tag `v<version>` points at the commit being built (annotated tags dereferenced). The Release half is not redundant with the tag half: a tag can exist with no Release behind it when its own run's `call-release` failed, and the guard's error message always claimed to be checking the Release -- so pushing `v0.4.0`, having `call-release` fail, and then dispatching from `main` with `publish_image_tag=0.4.0` used to publish an image with no Release behind it, the dangling artifact the job header names as the state to avoid. The documented recovery case is unaffected: republishing a Release whose image push failed is done by dispatching with the tag selected as the ref, where the tag path applies and the check holds by construction.
- CI: every third-party action on the publish path is pinned to a full commit SHA, and the pre-checkout `busybox:1` to a digest. Nothing in `.github/` was SHA-pinned; mutable major-version tags are a demonstrated attack vector (the tj-actions/changed-files incident retagged every version tag to malicious code), and this workflow hands `GITHUB_TOKEN` with `packages: write` to `docker/login-action@v4` and lets `docker/build-push-action@v7` do the push -- so a retag of either would have yielded the registry credential and the ability to publish arbitrary content to `ghcr.io/ycpss91255-docker/omniverse_web_viewer`, an image downstream consumers pin and execute. The `busybox` case is separately notable: it runs as root with the workspace bind-mounted, BEFORE checkout, on the persistent self-hosted GPU host. `ycpss91255-docker/base/...` reusable workflows stay on version tags deliberately -- they are first-party and their refs are the subject of their own tracked decisions (#37, #67, base#915). Note for whoever bumps these: there is no `github-actions` dependabot entry in this repo, so pins are manual today.
- CI: `contents: write` is no longer granted workflow-wide. It existed for `call-release` alone (softprops/action-gh-release needs it to create a Release), but as a workflow-level block every job inherited it -- `call-docker-build`, which runs on EVERY `pull_request`, and `tier-b-visual-e2e`, which runs on a persistent, shared, self-hosted GPU host. `actions/checkout` persists that token into `.git/config` on the runner, so the least-trusted job in the file (a build driven by a Dockerfile and build args that come from the PR branch) sat next to a token that can push commits and create tags -- and a `v*` tag is itself a trigger in this workflow, i.e. directly upstream of the release path. Branch protection does not contain it: only FORK PRs are forced read-only by GitHub, same-repo branch PRs get the full write token. All four jobs now declare their own scope (`contents: read`, plus `packages: write` for `publish-image`), and `contents: write` reaches `call-release` and nothing else.
- The published runtime image no longer carries `npm`, `npx`, `corepack`, `git` or `sudo`, and ADR-0001 no longer claims an invariant the built image did not hold. ADR-0001 says the deployable image carries "only `node` + `serve` ... no npm ... no dev toolchain", and `Dockerfile`'s runtime header repeated it -- but `runtime` is `FROM devel-base`, which apt-installs `sudo git curl ca-certificates` and a nodejs deb that brings `npm` + `corepack` along, so all of it shipped. On the published artifact, `command -v` found `/usr/bin/{git,curl,npm,node,sudo,serve}` and `/usr/lib/node_modules` held `corepack npm serve`. Two costs, and the second is the one that made this worth fixing: an attacker with a foothold had `curl` to fetch a payload and `npm`/`node` to run it, and -- more importantly -- a reader sizing the sidecar's blast radius from the ADR was reading a property the image did not have. The `runtime` stage now purges `git` + `sudo` (with `SUDO_FORCE_REMOVE`, since sudo's prerm refuses to uninstall itself when no root password is set -- for a container that is the goal, not the accident it warns about) and deletes the npm/corepack trees, `runtime-test` asserts their absence in-image so the claim is enforced rather than merely written, and ADR-0001 records what actually ships. `curl` STAYS, deliberately and now explicitly documented: it is the HTTP client of the two `FROM runtime` test stages (`RUNTIME_SMOKE_CMD` and `test/e2e/run-in-image.sh`), and removing it while `node` -- which has a global `fetch` -- remains would change that contract without changing what an attacker can do. The never-published `e2e-test` stage takes npm back from `devel-base`, so the shipped image is not carrying a package manager for a test stage's benefit.
- The published runtime image no longer grants its non-root user passwordless root. The `sys` stage ended with `echo "${USER_NAME} ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers`, and `runtime` is `FROM devel-base` is `FROM sys`, so every shipped image inherited it -- verified against the published artifact: `docker run --rm ghcr.io/ycpss91255-docker/omniverse_web_viewer:0.3.0-rc3 sh -c 'id; sudo -n id'` returns `uid=1000(ci)` and then `uid=0(root)`, no prompt. That nullified the image's own containment story: it is pushed publicly, pinned by downstream consumers (isaac#173), and run there on a network port with `--network=host`, so any code execution inside it -- a `serve`/Node vulnerability, a compromised dependency in the bundle's build -- escalated to container root with one `sudo`, and from there to bind-mounted host paths and the shared kernel surface. Nothing in the runtime ever needed it; only the two `*-build` stages and `devel` use `sudo`, and the first two are discarded. The grant now lives per-stage in `usd-viewer-build`, `stream-only-build` and `devel` (where passwordless sudo in an interactive dev container remains by design -- it is why `.hadolint.yaml` ignores DL3004), and the `runtime-test` stage asserts, as the runtime USER, that `sudo -n` cannot succeed, so the posture cannot silently regress again.

### Fixed
- Tier B: the most expensive failure mode no longer leaves nothing behind. Evidence was uploaded `if: failure()`, which does NOT run in a cancelled job -- and a `timeout-minutes` overrun cancels the job. So a Tier B that ran out of its 60 minutes uploaded nothing, and the next run's pre-checkout `rm -rf .tier-b-artifacts` destroyed the `producer.log` the driver had written (the file it calls "the only diagnosis a nightly failure leaves behind"). The acceptance step now carries its own `timeout-minutes: 45` inside the job's budget, so an overrun is a step FAILURE with the job's 60 left as a backstop, and the upload runs on `failure() || cancelled()` for the cancellations that still come from outside (the concurrency group, a manual cancel). `if-no-files-found` moves from `ignore` to `warn`, so an empty upload is no longer indistinguishable from a real one.
- Tests: the usd-viewer config-dial assertion is no longer dead code with an incomplete fallback. Its strong branch -- the only place `OWV_EXPECT_PORT` was asserted for usd-viewer -- is unreachable: the upstream sample starts on `Forms.AppOnly` and only reaches `AppStreamer.connect` after a Next click the spec never performs, so the 15 s poll always timed out into the fallback. That fallback checked the injected server and the absence of `__OWV_SERVER__`, but neither the port nor `__OWV_PORT__` -- the same gap that was closed on the stream-only side -- so an entrypoint regression that dropped `SIGNALING_PORT`, or a build that stopped emitting the port sentinel into the usd-viewer bundle, would have left the only per-PR cover usd-viewer has green. The fallback now asserts both values and both sentinels, and the unreachable window is 2 s instead of 15 s (kept, not deleted, so a future auto-dialing upstream still takes the stronger path), which also stops every PR run paying fifteen guaranteed seconds to reach a branch it cannot take.
- Tests: the per-PR browser gate now runs one Playwright project per invocation, so a suite that matches zero spec files fails instead of vanishing. `run-in-image.sh` selected `--project=chromium --project=chromium-loopback` in ONE run, and Playwright evaluates its "No tests found" guard over the whole selection: verified against the pinned `@playwright/test` 1.62.1, selecting the loopback project alone with its spec absent gives `Error: No tests found` and exit 1, while selecting both gives `1 skipped` and exit 0. So renaming or losing a spec file would have silently dropped it from the per-PR gate while the runner still printed `=== e2e: all modes passed ===`. `run-tier-b.sh` was never exposed, because it selects a single project.
- Tier B: a SIGNALLED run can no longer exit 0, i.e. report a verified picture having asserted nothing. `cleanup()` in `script/ci/tier_b_visual_e2e.sh` opened with `local rc=$?` and closed with `exit "${rc}"` while trapped on `EXIT INT TERM`; on a signal path `$?` is the last COMPLETED command's status -- the boot-wait loop's `sleep 5`, i.e. 0 -- not a failure. Sending `INT`/`TERM` to the script's pid alone therefore gave EXIT=0 (reproduced; only a process-GROUP signal happened to give 130/143). The script's own header says `Exit 0 = a real browser saw a real, non-black frame` and the workflow's picture gate hangs off that exit code, so a run killed by a GitHub step timeout or a job cancellation was indistinguishable from a run that saw a picture -- a hole in the rule that no version publishes unverified. The same function being both the signal handler and the EXIT handler also re-entered it through its own `exit`, so teardown ran twice and `producer.log` was written twice. `cleanup` now does teardown only and never touches the status (the shape the sibling runners `test/e2e/run-tier-b.sh` and `run-in-image.sh` always had), and INT/TERM get explicit handlers that exit 130/143. A new bats spec locks all three properties with a stubbed `docker` -- no GPU, Kit or daemon needed to ask what the exit status is. bats 49 -> 52.
- Tier B: the producer readiness poll no longer reports a marker that IS in the log as absent. `docker logs "${PRODUCER_NAME}" 2>&1 | grep -qF "${READY_MARKER}"` runs under `set -o pipefail`: `grep -q` exits on its first match, `docker logs` is still writing and dies of SIGPIPE (141), and pipefail hands that 141 up as the pipeline's status. It only misfires once the output is long enough for docker to still be writing when grep leaves -- so it passes every small reproduction and fails against a real multi-megabyte Kit log (reproduced here against real `docker logs`: marker on line 1 followed by ~183 KB of output gives MISS/141, where `grep -c` gives FOUND). This is the gate the release invariant hangs on: when it misfired the run burned the full 900 s boot timeout and exited 1 with "producer did not report ...", then printed a log tail visibly containing that line, blocking the tag's release and pointing the operator at a producer that was in fact ready. The two `docker ps | grep -qx` checks had the same defect -- one able to declare a running container exited, the other able to silently skip saving `producer.log`. All three now count with `grep -c`, which reads to EOF so docker never gets the signal.
- Tier B: `owv-tierb-*` containers left behind by a hard-killed run are now reaped. The producer is deliberately not `--rm` (its log is the only diagnosis a nightly failure leaves) and is removed only by the EXIT/INT/TERM trap, which a SIGKILL -- runner reboot, docker daemon restart, the GHA hard kill, the job's own `timeout-minutes` -- skips, leaving a Kit container holding `--gpus all` and the host network. Nothing removed it afterwards: the instance scope is `GITHUB_RUN_ID`, different on every run, so the pre-clean and teardown walked past it, and the workflow's pre-checkout step only deletes `.tier-b-artifacts`. The next Tier B then contended with a stale Kit for GPU memory and could fail for reasons unrelated to the viewer -- which under the release invariant is a blocked release with a misleading symptom, on a host nobody is watching. Startup now reaps the namespace with the isolation guarantee unchanged: candidates come from a `^owv-tierb-` filter and still pass through the prefix-refusing `_drop`, and only containers older than `TIER_B_ORPHAN_MAX_AGE_MIN` (default 120 min, twice the job's budget) are touched, so a concurrent instance is left alone.
- Tests: the `stream-only` config-dial spec now asserts the `pageerror` collector it had been registering and ignoring. `const pageErrors: string[] = []; page.on('pageerror', ...)` sat in the test with no matching `expect` anywhere in its body, while the sibling `usd-viewer` test in the same file consumed it -- so an uncaught exception in the app we OWN passed the per-PR gate silently, and only the upstream app we do not control was checked. It could pass on a throwing bundle: the `owv:dial` event is dispatched before the streaming library is wired, so a throw while wiring the status callbacks still leaves the primary assertion green and `#stream-status` neither in `error` nor reading `invalid`.
- Tests: `forbidOnly` in the Playwright config is hardcoded `true` instead of `!!process.env.CI`. No entry point ever sets `CI` -- `run-in-image.sh` is a Dockerfile `RUN` and the Tier B container is started with four `-e` flags, none of them `CI` -- so the guard was always off and a committed `test.only` would have narrowed either suite to a single test with both gates still green. That matters most for Tier B, which the release invariant rests on. There is no interactive or watch use of this config that a live `.only` would serve.
- Tests: the tier-1 config-dial gate now injects a signaling port that is not the built-in default, so its port assertion means something. `run-in-image.sh` set `TEST_SIGNALING_PORT="49100"` directly under a comment claiming the test values "cannot collide with any baked default (127.0.0.1 / 49100)" -- 49100 IS that default (Dockerfile `ENV`, the entrypoint fallback and `overlay/stream.config.json` all say so), so `expect(String(dial?.port)).toBe(EXPECT_PORT)` passed identically whether `SIGNALING_PORT` had been honoured or the entrypoint had fallen back. Nothing else closed the gap: every bats render assertion used 49100 too, and the only non-default port in the tree belongs to Tier B, which never runs per-PR -- so a regression that hardcoded or dropped `SIGNALING_PORT` would have shipped on a green PR and surfaced only in the nightly GPU job. The e2e now injects `49177`, and a new bats case (`usd-viewer applies SIGNALING_PORT env override`, mirroring the existing server-override case) renders `49277` through the real entrypoint and greps the active dist for it. bats 48 -> 49.
- Entrypoint: `SIGNALING_PORT` is now validated on the same terms `MEDIA_PORT` always was, and both gained a no-leading-zero rule. `SIGNALING_PORT` was checked only against `^[0-9]+$` -- no range, so `0` and `99999` reached the browser, and no leading-zero rule, which is the one that actually breaks. The port sed replaces the QUOTED sentinel `"__OWV_PORT__"`, so the value lands in the bundle as a BARE numeric token: `SIGNALING_PORT=049100` renders `signalingPort:049100`, which is `SyntaxError: Decimals with leading zeros are not allowed in strict mode`. The chunk fails to parse, the viewer is a black page -- and the entrypoint exits 0, `serve` answers HTTP 200, the runtime smoke passes and the bats render assertions pass, so nothing anywhere said why. A range test alone does not catch it either, because bash `[ x -lt y ]` parses base 10. Both ports now require an integer 1..65535 written without a leading zero, which is what the entrypoint header ("a bad value must fail the container fast rather than bake malformed JS") always claimed. `SERVE_PORT` gets the same rule, checked only when set (the `example` stage serves on `EXAMPLE_PORT`): it is not rendered into a bundle, but `SERVE_PORT=0` otherwise starts a viewer on a port nobody chose. Four new bats cases lock the rejections; bats 44 -> 48.

## [0.3.0] - 2026-08-26

First tagged release. Everything below shipped in it; `v0.3.0-rc1` .. `-rc3` were
the verification rounds on the way there, not separate feature sets.

### Changed
- The repo-level bats smoke specs moved to the tool-first layout `test/bats/smoke/<stage>/` (#70), adopting base's ADR-00000012 convention as of base v0.42.0. The leaf directory names the Dockerfile STAGE the specs are built to run in, so the specs a stage owns are exactly the ones its `COPY` names and a spec cannot drift into an image that cannot satisfy it. All three land in `test/bats/smoke/devel-test/`, which is a decision rather than a default: `derive_image_tag.bats` needs `/ci/` and `example_demo.bats` needs `/examples/`, neither of which exists outside `devel-test`; `omniverse_web_viewer_env.bats` asserts `/app/*/dist` + `/entrypoint.sh`, which the `runtime` stage also has, but this repo's `runtime-test` stage runs `RUNTIME_SMOKE_CMD` (serve + curl for HTTP 200), not bats, so a `shared/` tree would advertise a second consumer that does not exist -- if a runtime-test bats block is ever added, moving that one file to `shared/` is the whole change. The `devel-test` `COPY` follows the move; `.base/test/smoke/` still lands in the same `/smoke_test/`, both trees flatten there, and `load "${BATS_TEST_DIRNAME}/test_helper"` therefore keeps resolving. Nothing about what runs changes: the same 44 `@test` in the same stage. `test/e2e/` is deliberately NOT part of this -- its runners resolve self-relatively and its `COPY` is `test/e2e/ -> /e2e/`. A consequence rather than the motive: `test/bats/smoke/` is also the path base v0.42.0's `release-worker.yaml` archives, which is what lets the temporary SHA pin be retired below.
- `call-release` is back on a released base tag: `release-worker.yaml@v0.42.0` instead of the temporary commit-SHA pin `8f54fde0ca6232d07d4ba3e93522af08cd7cc50e`, and the block of comment explaining the pin is deleted (#70; this meets the condition #67 tracks). The pin existed because v0.42.0's archive step copies a fixed list of "standard" paths and hard-fails on any the consumer lacks, and that list names `test/bats/smoke/` while this repo's tree was `test/smoke/bats/`. The layout move above is what removes the mismatch, and it was made because base ADR-00000012 is the right convention, not to work around the list. Every path in the list -- `Dockerfile script/ .hadolint.yaml test/bats/smoke/ .base/ README.md doc/` -- was checked to exist in this tree before the ref moved. `call-docker-build` stays on `@v0.41.0`: moving the build worker is a separate change with its own verification (#37). The `.base` subtree also stays at v0.41.0 -- base#915 records that the v0.42.0 upgrade path is broken for a v0.41.0 consumer, so only the workflow ref moves. Caveat stated plainly: nothing in PR CI touches the archive step, so the only proof it now succeeds is the path-by-path check plus reading v0.42.0's `cp` list; the step itself is unverifiable without pushing a tag, which is the opacity base#914 is open about.
- `stream-only` viewer: producer loss is now detected from the picture as well as from the streaming library (closes #62). Until now the loss states were entered only from the library's `onStop` callback, which is the #58 failure mode one step removed -- a single opaque third-party callback deciding whether the user is ever told anything, and its sibling `onTerminate` had already turned out never to fire. `apps/stream-only/src/streamStatus.js` now also samples frame progress on `#remote-video` (`getVideoPlaybackQuality().totalVideoFrames`, falling back to `currentTime`) and, after `FRAME_STALL_SAMPLES` (5) consecutive `FRAME_STALL_POLL_MS` (1000 ms) samples with no progress, announces the SAME recoverable `stream stopped -- waiting for frames to resume...`, which escalates through the SAME `TERMINAL_ESCALATION_MS` timer to the SAME latched terminal `stream ended -- the source is gone. Reload once it is back.` (#57 / #58 / #60 all unchanged). User-visible effect: a picture that freezes without the library saying anything now produces the recoverable readout after about 5 seconds and the terminal one about 20 seconds after the freeze, where before it could stay frozen and silent indefinitely. `onStop` is kept wired as an ACCELERATOR -- it announces sooner than the poll can -- and a `lossAnnounced` guard means whichever notices first is the one that speaks, so the escalation is never re-armed and the terminal state still lands one window after the FIRST signal. The watchdog arms only after a frame has actually rendered and only for an element that can report progress, so a viewer that never connects (the dead-host `config-dial` e2e) and the DOM-free unit fakes are untouched. The residual assumption is recorded next to the constants: a live producer must keep delivering frames even when its scene is static (true for Kit, which encodes its render loop at a target frame rate); a producer that sent only on change would need a longer window.

### Fixed
- `stream-only` viewer: a stream that starts working late no longer sits under a permanent error (closes #73). Once the terminal state had latched, a real rendered frame could not clear it: `hide()` cancelled the escalation, cleared `lossAnnounced` and then returned early on `terminal`, discarding the proof. A viewer whose producer came up after the connect window expired therefore kept a red `no video from the source -- it never started. Check that it is running, then reload.` on top of a picture that was demonstrably playing, until the page was reloaded. Caught by the `v0.3.0-rc2` tag run, where the picture gate held and nothing published: terminal at 06:19:48.863, frames advancing at 06:19:50.997, a 1920x1080 sample with `meanLuma` 151.99 (identical to a passing run), and the error div still there when the assertion timed out at 06:20:21. The frame arrived 2 seconds after the window closed; only the readout was wrong. The latch itself is right and stays -- #63 added it because `onStart` fires optimistically on every session-start retry, so a retry could otherwise repaint `streaming <server>:<port>` over a genuine failure. What changes is what it outranks: **claims, not observation**. The callback-derived paths (`show()` from `onStart`, `connecting()`, `stopped()`) still cannot touch a terminal state, exactly as #63 established. The media-derived paths can: `hide()` from a `playing` / `loadeddata` event, and the frame-progress watchdog, now clear the readout AND un-latch, but only on evidence -- frame progress that has ADVANCED past the reading taken at the instant the latch closed (`terminalProgress`). That qualifier is what preserves the #63 case: a stream that never delivers a frame reports the same reading forever, or none at all, so nothing can reopen its terminal state, and a bare `playing` event with no frame behind it stays a claim like any other. `terminate()` also keeps the watchdog running instead of cancelling it, repurposed from a stall watch into a recovery watch -- after a stall long enough to escalate, `playing` does not necessarily re-fire, so the poll is how a resumed stream gets noticed. A recovered viewer is fully live again, not merely un-hidden: a later stall re-announces the recoverable state and re-escalates normally. Recovery is silent by design -- the user is looking at a working picture and does not need to be told about a verdict that turned out wrong -- and the error styling is withdrawn with the verdict. `CONNECT_ESCALATION_MS` stays at 20 s, decided rather than defaulted: a window that now ends in a verdict a real frame can withdraw costs, when it fires early, a message that clears itself, while every second added to it is a second a genuinely dead producer goes unreported. Against a cold producer (rc2's first frame was ~22 s after page load) the message does still appear briefly before clearing; that is the intended remaining cost. Five unit specs and one browser spec cover it, plus two existing specs that had encoded the defect and now assert the opposite -- the `status-loopback.spec.ts` escalation spec (a fresh real stream after a real escalation clears the readout, where it used to assert it could not) and the #62 watchdog-latch unit spec.

### Changed
- Base subtree bumped `v0.34.1` -> `v0.41.0` (#43). Container ops move from `make` to `just` (root `Makefile` symlink replaced by `justfile`; e.g. `make run -- -t serve -d` -> `just run -t serve -d`, no `--` separator needed). The entrypoint now runs under `set -euo pipefail`, validates every resolved value (signaling-server charset, numeric port, `ui_mode` / `auto_launch` enums) and exits non-zero on invalid input instead of baking malformed JS or injecting sed/JS metacharacters, and strips trailing inline `# comments` from `host.yaml` values. Behavior change: a previously-silent bad value now fails the container fast. The served `*.js` is re-rendered from pristine `*.js.tmpl` templates on every boot (built once, preserved in the image), so a `docker restart` or a changed env / `host.yaml` is picked up on the next start — the old in-place edit baked the first-boot values and ignored later changes.
