## [Unreleased]

### Fixed
- Tests: the tier-1 config-dial gate now injects a signaling port that is not the built-in default, so its port assertion means something. `run-in-image.sh` set `TEST_SIGNALING_PORT="49100"` directly under a comment claiming the test values "cannot collide with any baked default (127.0.0.1 / 49100)" -- 49100 IS that default (Dockerfile `ENV`, the entrypoint fallback and `overlay/stream.config.json` all say so), so `expect(String(dial?.port)).toBe(EXPECT_PORT)` passed identically whether `SIGNALING_PORT` had been honoured or the entrypoint had fallen back. Nothing else closed the gap: every bats render assertion used 49100 too, and the only non-default port in the tree belongs to Tier B, which never runs per-PR -- so a regression that hardcoded or dropped `SIGNALING_PORT` would have shipped on a green PR and surfaced only in the nightly GPU job. The e2e now injects `49177`, and a new bats case (`usd-viewer applies SIGNALING_PORT env override`, mirroring the existing server-override case) renders `49277` through the real entrypoint and greps the active dist for it. bats 48 -> 49.
- Entrypoint: `SIGNALING_PORT` is now validated on the same terms `MEDIA_PORT` always was, and both gained a no-leading-zero rule. `SIGNALING_PORT` was checked only against `^[0-9]+$` -- no range, so `0` and `99999` reached the browser, and no leading-zero rule, which is the one that actually breaks. The port sed replaces the QUOTED sentinel `"__OWV_PORT__"`, so the value lands in the bundle as a BARE numeric token: `SIGNALING_PORT=049100` renders `signalingPort:049100`, which is `SyntaxError: Decimals with leading zeros are not allowed in strict mode`. The chunk fails to parse, the viewer is a black page -- and the entrypoint exits 0, `serve` answers HTTP 200, the runtime smoke passes and the bats render assertions pass, so nothing anywhere said why. A range test alone does not catch it either, because bash `[ x -lt y ]` parses base 10. Both ports now require an integer 1..65535 written without a leading zero, which is what the entrypoint header ("a bad value must fail the container fast rather than bake malformed JS") always claimed. `SERVE_PORT` gets the same rule, checked only when set (the `example` stage serves on `EXAMPLE_PORT`): it is not rendered into a bundle, but `SERVE_PORT=0` otherwise starts a viewer on a port nobody chose. Four new bats cases lock the rejections; bats 44 -> 48.

## [0.3.0] - 2026-08-26

First tagged release. Everything below shipped in it; `v0.3.0-rc1` .. `-rc3` were
the verification rounds on the way there, not separate feature sets.

### Changed
- The repo-level bats smoke specs moved to the tool-first layout `test/bats/smoke/<stage>/` (#70), adopting base's ADR-00000012 convention as of base v0.42.0. The leaf directory names the Dockerfile STAGE the specs are built to run in, so the specs a stage owns are exactly the ones its `COPY` names and a spec cannot drift into an image that cannot satisfy it. All three land in `test/bats/smoke/devel-test/`, which is a decision rather than a default: `derive_image_tag.bats` needs `/ci/` and `example_demo.bats` needs `/examples/`, neither of which exists outside `devel-test`; `omniverse_web_viewer_env.bats` asserts `/app/*/dist` + `/entrypoint.sh`, which the `runtime` stage also has, but this repo's `runtime-test` stage runs `RUNTIME_SMOKE_CMD` (serve + curl for HTTP 200), not bats, so a `shared/` tree would advertise a second consumer that does not exist -- if a runtime-test bats block is ever added, moving that one file to `shared/` is the whole change. The `devel-test` `COPY` follows the move; `.base/test/smoke/` still lands in the same `/smoke_test/`, both trees flatten there, and `load "${BATS_TEST_DIRNAME}/test_helper"` therefore keeps resolving. Nothing about what runs changes: the same 44 `@test` in the same stage. `test/e2e/` is deliberately NOT part of this -- its runners resolve self-relatively and its `COPY` is `test/e2e/ -> /e2e/`. A consequence rather than the motive: `test/bats/smoke/` is also the path base v0.42.0's `release-worker.yaml` archives, which is what lets the temporary SHA pin be retired below.
- `call-release` is back on a released base tag: `release-worker.yaml@v0.42.0` instead of the temporary commit-SHA pin `8f54fde0ca6232d07d4ba3e93522af08cd7cc50e`, and the block of comment explaining the pin is deleted (#70; this meets the condition #67 tracks). The pin existed because v0.42.0's archive step copies a fixed list of "standard" paths and hard-fails on any the consumer lacks, and that list names `test/bats/smoke/` while this repo's tree was `test/smoke/bats/`. The layout move above is what removes the mismatch, and it was made because base ADR-00000012 is the right convention, not to work around the list. Every path in the list -- `Dockerfile script/ .hadolint.yaml test/bats/smoke/ .base/ README.md doc/` -- was checked to exist in this tree before the ref moved. `call-docker-build` stays on `@v0.41.0`: moving the build worker is a separate change with its own verification (#37). The `.base` subtree also stays at v0.41.0 -- base#915 records that the v0.42.0 upgrade path is broken for a v0.41.0 consumer, so only the workflow ref moves. Caveat stated plainly: nothing in PR CI touches the archive step, so the only proof it now succeeds is the path-by-path check plus reading v0.42.0's `cp` list; the step itself is unverifiable without pushing a tag, which is the opacity base#914 is open about.
- `stream-only` viewer: producer loss is now detected from the picture as well as from the streaming library (closes #62). Until now the loss states were entered only from the library's `onStop` callback, which is the #58 failure mode one step removed -- a single opaque third-party callback deciding whether the user is ever told anything, and its sibling `onTerminate` had already turned out never to fire. `apps/stream-only/src/streamStatus.js` now also samples frame progress on `#remote-video` (`getVideoPlaybackQuality().totalVideoFrames`, falling back to `currentTime`) and, after `FRAME_STALL_SAMPLES` (5) consecutive `FRAME_STALL_POLL_MS` (1000 ms) samples with no progress, announces the SAME recoverable `stream stopped -- waiting for frames to resume...`, which escalates through the SAME `TERMINAL_ESCALATION_MS` timer to the SAME latched terminal `stream ended -- the source is gone. Reload once it is back.` (#57 / #58 / #60 all unchanged). User-visible effect: a picture that freezes without the library saying anything now produces the recoverable readout after about 5 seconds and the terminal one about 20 seconds after the freeze, where before it could stay frozen and silent indefinitely. `onStop` is kept wired as an ACCELERATOR -- it announces sooner than the poll can -- and a `lossAnnounced` guard means whichever notices first is the one that speaks, so the escalation is never re-armed and the terminal state still lands one window after the FIRST signal. The watchdog arms only after a frame has actually rendered and only for an element that can report progress, so a viewer that never connects (the dead-host `config-dial` e2e) and the DOM-free unit fakes are untouched. The residual assumption is recorded next to the constants: a live producer must keep delivering frames even when its scene is static (true for Kit, which encodes its render loop at a target frame rate); a producer that sent only on change would need a longer window.

### Fixed
- `stream-only` viewer: a stream that starts working late no longer sits under a permanent error (closes #73). Once the terminal state had latched, a real rendered frame could not clear it: `hide()` cancelled the escalation, cleared `lossAnnounced` and then returned early on `terminal`, discarding the proof. A viewer whose producer came up after the connect window expired therefore kept a red `no video from the source -- it never started. Check that it is running, then reload.` on top of a picture that was demonstrably playing, until the page was reloaded. Caught by the `v0.3.0-rc2` tag run, where the picture gate held and nothing published: terminal at 06:19:48.863, frames advancing at 06:19:50.997, a 1920x1080 sample with `meanLuma` 151.99 (identical to a passing run), and the error div still there when the assertion timed out at 06:20:21. The frame arrived 2 seconds after the window closed; only the readout was wrong. The latch itself is right and stays -- #63 added it because `onStart` fires optimistically on every session-start retry, so a retry could otherwise repaint `streaming <server>:<port>` over a genuine failure. What changes is what it outranks: **claims, not observation**. The callback-derived paths (`show()` from `onStart`, `connecting()`, `stopped()`) still cannot touch a terminal state, exactly as #63 established. The media-derived paths can: `hide()` from a `playing` / `loadeddata` event, and the frame-progress watchdog, now clear the readout AND un-latch, but only on evidence -- frame progress that has ADVANCED past the reading taken at the instant the latch closed (`terminalProgress`). That qualifier is what preserves the #63 case: a stream that never delivers a frame reports the same reading forever, or none at all, so nothing can reopen its terminal state, and a bare `playing` event with no frame behind it stays a claim like any other. `terminate()` also keeps the watchdog running instead of cancelling it, repurposed from a stall watch into a recovery watch -- after a stall long enough to escalate, `playing` does not necessarily re-fire, so the poll is how a resumed stream gets noticed. A recovered viewer is fully live again, not merely un-hidden: a later stall re-announces the recoverable state and re-escalates normally. Recovery is silent by design -- the user is looking at a working picture and does not need to be told about a verdict that turned out wrong -- and the error styling is withdrawn with the verdict. `CONNECT_ESCALATION_MS` stays at 20 s, decided rather than defaulted: a window that now ends in a verdict a real frame can withdraw costs, when it fires early, a message that clears itself, while every second added to it is a second a genuinely dead producer goes unreported. Against a cold producer (rc2's first frame was ~22 s after page load) the message does still appear briefly before clearing; that is the intended remaining cost. Five unit specs and one browser spec cover it, plus two existing specs that had encoded the defect and now assert the opposite -- the `status-loopback.spec.ts` escalation spec (a fresh real stream after a real escalation clears the readout, where it used to assert it could not) and the #62 watchdog-latch unit spec.
- CI: no version can be published without the picture having been verified (closes #70). `v0.3.0-rc1` was cut and its image pushed while the Tier B visual acceptance -- the gate built in #48 precisely to prove a real Kit producer renders a real picture -- never ran for that commit: `tier-b-visual-e2e` was gated on `schedule` / `workflow_dispatch` only, so a tag push skipped it, and `publish-image` needed only `[call-docker-build, call-release]`. The tag run recorded it plainly (`tier-b-visual-e2e: skipped`, `call-release: success`, `publish-image: success`). `tier-b-visual-e2e` now also runs on a tag ref, `call-release` takes it as a hard `needs`, and `publish-image` requires `needs.tier-b-visual-e2e.result == 'success'` outright -- skipped, failed, cancelled and timed-out all block the release and the image. The manual `publish_image_tag` escape hatch is gated the same way rather than left as a hole: a non-empty value makes the Tier B job run for that dispatch too, so there is no path to a published artifact that bypasses the picture. **There is deliberately no override**: no input, no `continue-on-error`, no `if: always()`. `call-release`'s condition contains no status function at all, so a skipped Tier B propagates as a skip by GitHub's default rule -- an unavailable GPU runner BLOCKS the release, which is the accepted and intended consequence, because an override on this gate would be reached for exactly when it matters most. Non-release triggers are unchanged: `pull_request` and `main` pushes still skip all three jobs, and the nightly `schedule` still runs Tier B alone with no release and no publish. One operational cost is recorded next to the job: the `concurrency` group serialises the GPU, so a tag pushed during the nightly run queues behind it.
- `stream-only` viewer: a viewer whose producer never answers no longer claims to be streaming, and a retry can no longer overwrite the terminal state (closes #63). The app mapped the streaming library's `onStart` straight onto a `streaming <server>:<port>` readout, but `onStart` fires when a connect ATTEMPT begins and re-fires on every session-start retry -- observed five times in a headless probe against a producer whose signaling port was down, with the page reading `streaming 10.2.23.83:49200`, in the non-error base colour, unchanged for the whole run. Nothing rescued it: no frame means no `hide()` and no frame-progress watchdog (#62 arms it only after a frame has rendered), and no session means no `onStop` and no #58 escalation. The connect attempt is now a state of its own: `createStatusController` gains `connecting(text)`, which shows the attempting readout and arms a bounded window (`CONNECT_ESCALATION_MS`, 20 s, injectable as `connectDelayMs`) from the FIRST attempt; `main.ts` calls it once before connecting -- so the window exists even if `onStart` never fires at all -- and hands the same call to `onStart`, whose repeats are ignored rather than pushing the deadline back. A rendered frame cancels it through the existing `hide()` path, so a stream that really comes up is untouched. If the window elapses with no frame, the readout becomes the actionable, latched `no video from the source -- it never started. Check that it is running, then reload.`, deliberately distinct from the mid-session `stream ended -- the source is gone. Reload once it is back.`: nothing ended when nothing ever started, and the user's next move differs. Second defect, same family: `show()` was the only method without the terminal guard `hide()` and `stopped()` have, so a retry could resurrect a false `streaming ...` over the latched terminal message -- it now has it, and both terminal states share one `terminate(text)` helper. User-visible copy change: the connect-time readout is `connecting to <server>:<port>...` instead of `streaming <server>:<port>`, because until a frame renders the viewer knows only that it is trying. The 20 s window is longer than the 15 s mid-session escalation on purpose (a viewer opened before the Kit app has booted is ordinary, and the library keeps retrying session start meanwhile) and far longer than the `config-dial` e2e, which dials a dead host and asserts no `error` class -- that suite completes in about 90 ms per mode, and a unit spec locks the lower bound. Ten unit specs and one browser spec (`status-loopback.spec.ts`, no loopback: the never-connected case) cover it; #53 / #57 / #58 / #60 / #62 behaviour is otherwise unchanged, and `connecting()` defers to an announced producer loss instead of overwriting it.
- `stream-only` viewer: the recoverable producer-loss readout no longer claims a reconnect is under way (closes #60). It read `stream stopped -- reconnecting...`, but nothing reconnects: in the bundle shipped in the runtime image (`/app/stream-only/dist/assets/omniverse-webrtc-streaming-library-*.js`) `maxReconnects` is passed straight through as `maxSessionStartRetry` (`new bv({ maxSessionStartRetry: o.maxReconnects, ... })`) and every use of `sessionStartRetryLeft` belongs to the session-**start** retry decision (`> 0`, `-= 1`, `= 0`) — there is no mid-session reconnect path, so a producer that dies once the stream is up is never reconnected to. The message therefore promised a recovery that could not happen, for the whole ~15 s before the terminal state (#58 / #59) replaced it. The recoverable state now reads `stream stopped -- waiting for frames to resume...`, which is true whether or not the picture comes back. Copy change only: the state stays non-error (grey), still clears on the first rendered frame (#53), still escalates to the terminal `stream ended -- the source is gone. Reload once it is back.` after `TERMINAL_ESCALATION_MS` (#58 / #59), and the terminal latch (#57) is unchanged. `maxReconnects` is deliberately still 20 — it buys startup grace for a viewer opened before the Kit app finishes booting, and the explanatory comment in `packages/stream-core/src/buildStreamConfig.js` now also records that the viewer copy matches what the budget really does. A new unit spec locks the regression: neither producer-loss state may mention a reconnect.
- `stream-only` viewer: the terminal producer-loss state is reachable again (closes #58). #56 / #57 wired it to the streaming library's `onTerminate` handler, but **this library build never invokes that handler**, so a viewer whose producer had died sat on the recoverable `stream stopped -- reconnecting...` forever. Evidence, from the bundle shipped in the runtime image (`/app/stream-only/dist/assets/omniverse-webrtc-streaming-library-*.js`): `onTerminate` occurs exactly 4 times and none is a call site — twice as the error-code enum `SessionTerminatedByAnotherClient`, once inside the matching error message, once as the null entry of the defaults object; by contrast `onStart` (52), `onUpdate` (13) and `onStop` (7, with a real `onStopResult.bind(this)` dispatch) all have one. Confirmed live by SIGKILLing the Kit producer. The terminal state is now derived locally: `stopped()` arms a bounded escalation timer (`TERMINAL_ESCALATION_MS`, 15s) and, if no frame renders inside that window, escalates to the terminal `stream ended -- the source is gone. Reload once it is back.` — so the user-visible change is that the message now appears about 15 seconds after the picture stops, instead of never. A stream that comes back renders a frame, which disarms the escalation and clears the readout exactly as before (#53). The timer is injectable (`terminalDelayMs` / `setTimer` / `clearTimer`), so the unit specs cover escalate-on-timeout, cancel-on-recovery, re-arming and the #57 latch without any real waiting. `onStop` is unchanged; `onTerminate` stays wired as a belt-and-braces extra only, with the evidence recorded in `streamStatus.js` / `main.ts` so it is not assumed to fire again. `maxReconnects` was reviewed while here and deliberately left at 20 (library default 5): the bundle passes it through as `maxSessionStartRetry` and consumes it only in the session-**start** retry decision, so it plays no part in mid-session producer loss — lowering it would not make the terminal state arrive sooner and would only shorten the startup grace window for a viewer opened before the Kit app finishes booting.
- `stream-only` viewer: a producer that disappears mid-session is no longer silent (closes #56). The app wired only the streaming library's `onStart` handler, so a Kit process that died after the stream had started produced no UI change at all — since #53 the readout hides on the first rendered frame, the end state was a frozen or blank viewport with no text, while the library kept reconnecting in the background (`maxReconnects: 20`). `onStop` and `onTerminate` are now wired to two new `createStatusController` transitions: `stopped()` re-shows the readout as a recoverable `stream stopped -- reconnecting...` (a successful reconnect renders a frame, which clears it again), and `terminated()` shows a distinct terminal error (`stream ended -- the source is gone. Reload once it is back.`) that is sticky — a trailing stop or a stray video event cannot clear it. Both are consumed as bare signals (the library's message payload for these two handlers is not verifiable from this repo). The normal path is unchanged: the readout still clears on the first rendered frame (#53). `main.ts` stays thin DOM glue; the policy lives in `apps/stream-only/src/streamStatus.js` with `node --test` unit coverage.
- `stream-only` viewer: the `#stream-status` readout no longer persists as a centered caption over the live video (closes #53). It was set to `streaming <server>:<port>` on connect and never cleared, so the connect-time confirmation stayed on top of the rendering stream and reappeared on every reconnect. The readout is now hidden once `#remote-video` is actually rendering (first `playing` / `loadeddata` event) and re-shown only on error / reconnect, so it reads as the transient "connected to X" confirmation it was meant to be. The show/hide logic is extracted into `apps/stream-only/src/streamStatus.js` (`createStatusController`) with `node --test` unit coverage; `main.ts` stays thin DOM glue.

### Added
- A git tag now emits BOTH a GitHub Release and a matching GHCR image, from one run (closes #66). Until now this repo published no container image at all: `build-worker.yaml` passes `push: false` to every build and carries neither `docker/login-action` nor `packages: write`, and `release-worker.yaml` only attaches a source archive to a Release -- so the only way to get the viewer was to build it, which is why the downstream Tier B consumer (isaac#173) had to test against whatever the `web_viewer` submodule happened to point at. A new `publish-image` job in `.github/workflows/main.yaml` pushes the lean `runtime` stage (built dists + `serve`, no toolchain / `src/` / node_modules -- what a consumer actually runs) to `ghcr.io/ycpss91255-docker/omniverse_web_viewer`, in the SAME workflow run, from the SAME commit, as the Release. **The image tag is derived from the git ref, never hand-entered** (`script/ci/derive_image_tag.sh`: `v0.3.0` -> `:0.3.0`, `v0.3.0-rc1` -> `:0.3.0-rc1`), which is what makes the release and its image structurally unable to drift; an rc tag is first-class, since the rc is what gets verified before the final tag is cut. The job is gated on BOTH the build/test gate and the Release having succeeded, so no image is ever published behind a failed gate or without a Release to trace it back to; nothing publishes on a PR or a `main` push. `workflow_dispatch` keeps an escape hatch (`publish_image_tag`) for a manual publish off a non-tag ref -- it is IGNORED on a tag ref, where the tag itself wins. Guard: `test/smoke/bats/derive_image_tag.bats` (14 tests) exercises the deriver over the full table of refs a real push produces -- the one part of the tag path provable without pushing a tag -- and the `devel-test` stage now also ShellCheck-lints `script/ci/`, which nothing was linting before. bats 30 -> 44.
- Tier B visual acceptance: CI now proves there is actually a picture (closes #48). A nightly `tier-b-visual-e2e` job in `.github/workflows/main.yaml` (`runs-on: [self-hosted, gpu]`, `schedule` + a `workflow_dispatch` opt-in input, never per-PR) boots the pinned deterministic Kit producer `ghcr.io/ycpss91255-docker/isaac-stream-source:0.0.1` (isaac#223 / isaac PR #243 -- DomeLight + DistantLight over a 12x12 procedurally built checkerboard floor, fixed camera, RTX auto-exposure disabled, so a connecting browser always gets a non-black frame), waits for the producer's own `Streaming server started.` marker, then runs the existing `e2e-test` image at container runtime against it. That image is `FROM runtime`, so one container is both the viewer (the REAL `stream-only` dist rendered by the production entrypoint and pointed at the real producer) and the browser. `test/e2e/tier-b-visual.spec.ts` (project `chromium-tier-b`) then asserts, in ONE test owning ONE live session, what nothing in this repo could assert before: an `RTCPeerConnection` reaching `connected`, a remote track arriving, `#remote-video` reporting `videoWidth > 0` and decoding frames, and -- the point of the whole exercise -- that a frame sampled off the element is NOT BLACK (`drawImage` into a canvas downscaled to 320 px wide, every 7th pixel reduced to Rec.709 luma: mean >= 8, brightest >= 32, >= 10% of samples above the black floor). The #53 readout-clearing path is closed end-to-end against a real stream as the fifth assertion. Verified on a GPU host end to end: 1920x1080, mean luma 151.9, 99.99% of sampled pixels above the black floor, and the saved frame is the producer's checkerboard. Everything per-PR stopped one step short of this: `config-dial.spec.ts` dials a dead host, and `status-loopback.spec.ts` proves the viewer's REACTION to media using a canvas it paints itself. Two deliberate scope corrections against #48 as written, both stated here so they read as decisions rather than omissions. (1) `stream-only` ONLY, not both modes: #18 established that `usd-viewer` (the upstream sample, built UNMODIFIED per D2) only works with the kit-app-template USD Viewer and blanks against Isaac Sim / other Kit apps BY DESIGN, so asserting a picture there would fail forever; `usd-viewer` keeps its existing per-PR config-dial cover. (2) #48's Phase 1 (a synthetic Kit-signaling source) is dropped, not deferred: the issue itself flagged the hidden cost, and the NVIDIA streaming library is coupled to Kit's proprietary signaling handshake rather than generic WebRTC, so emulating it means re-implementing Kit signaling -- Phase 2 with the real producer supersedes it and asserts strictly more. Isolation is a hard requirement of #48 and is enforced structurally (the incident class is isaac#237 / #239 / #240 / #241, CI actors on a shared GPU host tearing down a manual stack): `script/ci/tier_b_visual_e2e.sh` names every container it creates `owv-tierb-<instance>-*` and its teardown REFUSES any name outside that prefix, both containers run `--rm` so nothing needs a project-wide `compose down`, ports are probed free with bash `/dev/tcp` starting from 5399 / 49399 (well clear of the 5173/49100 and 5174/49200 the dev and demo stacks have held), and nothing touches a compose project, an image tag or a shared name. On failure the job uploads the sampled frame PNG, the luma stats, the Playwright trace and the producer's container log. Four producer-side findings came out of wiring this, all filed upstream and all worked around here behind overridable knobs. (1) The published image cannot run the command its own README documents: `COPY --chmod=0644` also set 0644 on the parent directory it created, leaving `/opt/isaac-producer` without an execute bit, so the non-root image `USER` cannot traverse it and the container exits 1 on `[Errno 13] Permission denied` reading its own baked driver (ycpss91255-docker/isaac#244). The producer is therefore started with `--user 0:0`, behind `TIER_B_PRODUCER_USER`. (2) `--ipc=host` is required and is not in the documented start command: Kit boots fine on the default private 64 MB `/dev/shm`, but the streaming media pipeline allocates shared memory when a client ATTACHES, so its absence is invisible to any check that stops at "the signaling port is up" and shows up only once a browser connects -- which is exactly what this tier does. Adding it took time-to-first-frame from about 16 s to 1.9 s; the isaac repo already sets `ipc = host` in its own `setup.conf`, which is why compose-run stacks never hit this and a bare `docker run` does. (3) The readiness marker matters: `Streaming server started.` fires about 11 s before the scene exists (measured ~14 s vs `app ready` ~25 s vs the driver's own `[PRODUCER] empty lit stage streaming` ~26 s), and a client connecting in that window gets a session Kit then tears down as the driver takes the app over. The orchestrator waits for the driver's line instead -- the same lesson isaac#233 records, that "the port is listening" and "streaming works" are different claims. (4) The producer's FIRST session after boot never delivers video while the second and subsequent ones do (measured on one producer: 0 frames vs 3521 vs 3525 in 60 s; ycpss91255-docker/isaac#245), so the spec runs a bounded, logged warm-up that reloads until frames are ADVANCING -- not merely non-zero, since a single frozen frame satisfies that and a frozen frame is the false green this tier exists to remove. A producer that never streams exhausts the attempts and fails the run, so none of these workarounds can mask a regression. The per-PR gate is unchanged in behaviour: `run-in-image.sh` now names its two projects explicitly so the new one cannot be picked up by a build-time `RUN`.
- Browser-level assertions on the `#stream-status` state machine, driven by an in-page WebRTC loopback (closes #62). `test/e2e/status-loopback.spec.ts` builds a canvas `captureStream()` -> local `RTCPeerConnection` pair -> the page's own `#remote-video`, which produces REAL `loadeddata` / `playing` events with real decoded frames behind them -- no GPU, no Isaac, no Kit, no extra service -- and then asserts in a real browser what the unit specs structurally cannot: that the readout is genuinely hidden by the real stylesheet once frames render (computed `display: none`, not a class in a `Set`), that the initial and loss states carry the colours `index.html` actually declares (`rgb(139, 148, 158)` vs `rgb(248, 81, 73)`), and that the recoverable and terminal states are distinguishable. Cutting the media at the sender reaches the loss states with no producer involved, which is only possible because of the frame-progress detection above; a stall held past the escalation window reaches the terminal state, and a fresh loopback stream afterwards does not clear it (#57).
